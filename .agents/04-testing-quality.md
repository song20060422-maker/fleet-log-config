# 04-testing-quality.md — 测试、覆盖率、缺陷闭环与逐项验收

## 1. 覆盖率门禁

- 自编 Go 生产代码**整体语句覆盖率 ≥85%**，**各核心业务包分别 ≥85%**。
- 集成测试覆盖率**不得**替代单元测试覆盖率。
- 自动生成文件（GoFrame 脚手架生成物，如 `hack/`、模板生成的样板）可排除；自编数据库访问、HTTP 处理代码**不得自行排除**；其他排除项须教师事先明确并在报告列出，附排除清单与理由。
- 提交物：测试命令、原始输出、覆盖率原始文件（如 coverage.out / cover.html）、可读报告。

## 2. 必测路径（对应 `02-business-rules.md` 编号）

- **R1**：间隔边界 10/300 秒（含与 9/301 拒绝）；审批人=申请人拒绝；批准后参数修改拒绝；退回后再提交。
- **R2**：同车队并发创建第二个未结束活动被拒绝（并发用例须可重复执行）；未试点车拉取不到配置；试点未全成功时推广被拒绝；两台试点成功后推广放行。
- **R3**：车辆只能拉取面向自己的最新已发布版本；每车版本独立递增（含恢复更高版本）；下发不改生效值。
- **R4**：回执鉴权失败拒绝；重复成功幂等；旧版本迟到回执不覆盖新生效值；未知版本拒绝；跨车回执拒绝；全部留痕可查。失败回执不改此前生效值。
- **R5**：60s 超时显示与历史保留；当前版本迟到成功翻转结果且保留超时历史；失败不改生效值；已停止活动不因迟到回执重启。
- **R6/R7**：停止保留已发/未发范围与生效记录；恢复仅覆盖曾发布车辆（版本更高、目标=活动前值）；全部成功才可记完成；有未确认项禁止"全部恢复"。
- **R8**：越权操作（改请求里的用户/车辆编号）被拒并留痕；重复批准/推广/停止为幂等或明确拒绝；非法状态操作被拒。
- **并发**：同车队并发建活动、回执与状态翻转并发 → `-race` 无竞争且结果一致。
- **持久化**：真实数据库集成/接口测试；服务重启后业务结果仍可查询（V21）。

## 3. 质量检查命令

- `gofmt` 检查、`go vet ./...` 必须通过。
- 共享并发访问的逻辑（活动创建、回执处理、状态翻转）必须执行 `go test -race`，且并发验证**可重复执行**（多次运行结果一致）。
- 质量检查失败**不得继续发布**（与 `05-git-workflow.md` 门禁联动）。

## 4. 禁止事项

- 禁止删除失败测试、弱化断言、`t.Skip` 关键路径、排除生产代码凑覆盖率。
- 禁止写"永远通过"的空测试或断言仅判 err==nil 的伪测试。
- 禁止编造测试输出；报告中的数字必须能由提交的命令复现。

## 5. 缺陷登记与复测闭环

缺陷台账（编号 `BUG-001` 起连续）每条按以下字段登记：

| 字段 | 要求 |
|------|------|
| 来源用例 | 用例编号 + 对应题面规则 R<条款号> |
| 被测版本 | 分支 / 提交哈希 |
| 严重级别 | 阻断 / 严重 / 一般 / 轻微 |
| 复现步骤 | 可执行的接口请求或页面操作序列（含测试账号） |
| 期望结果 | **引用题面原文条款** |
| 实际结果 | 含证据（响应内容、数据库查询结果、截图索引） |
| 状态 | 待修复 → 已修复待复测 → 复测通过 / 遗留风险（需学生确认） |
| 修复与复测 | fix 提交哈希 + 编号；复测日期、回归范围、结果、证据位置 |

流程：

1. 测试 Agent 登记缺陷（复现步骤、预期/实际、对应验收点编号）。
2. 开发 Agent 在开发分支修复，**不得顺手改无关代码**。
3. 复测范围 = 触发用例 + 同规则关联用例 + 受影响场景回归；修复涉及生产代码必须重跑 `go test ./... -cover -race` 且覆盖率仍 ≥85%。
4. 复测记录关联原缺陷编号；验收后再次修改业务代码须重新核查受影响项（对应共同要求 §6）。

## 6. 数据与持久化验证

- 数据库集成/接口测试结果须提交（如内存外真实 DB 的用例）。
- 必须有"服务重启后业务结果仍可查询"（V21）的验证证据：重启前记录申请/活动/逐车期望值/生效值/版本/回执及拒绝记录，重启后逐项一致。

## 7. 逐项验收点（V1~V24，验收 Agent 只读引用、在验收报告中逐项给结论）

| # | 验收点（题面依据） |
|---|---|
| V1 | 申请含原因+五台车+间隔 10~300 校验；审批人=申请人被拒绝（R1） |
| V2 | 退回后可修改再提交；批准后参数不可原地修改（R1） |
| V3 | 同车队存在未结束活动时新活动被拒绝（R2） |
| V4 | 未试点车拉取不到活动配置（R2） |
| V5 | 试点未全成功时推广被拒绝，不得绕过（R2） |
| V6 | 两台试点（以有效成功回执判定）成功后可推广剩余三台（R2） |
| V7 | 车辆只取得面向自己的最新已发布版本；版本按车递增（R3） |
| V8 | 每车分别持久化期望值与已生效值；下发不改变生效值（R3） |
| V9 | 回执鉴权失败被拒绝并记录（R4） |
| V10 | 重复成功回执幂等不重复记账（R4） |
| V11 | 旧版本迟到回执不覆盖新生效值，仅留痕（R4/R5） |
| V12 | 未知版本、跨车回执被拒绝并记录（R4） |
| V13 | 60s 无有效回执显示超时且保留超时历史；迟到成功翻转结果并保留历史（R5） |
| V14 | 失败回执不改变此前生效值（R5） |
| V15 | 已停止活动不因迟到回执自动重启（R5） |
| V16 | 停止仅阻止未发布部分；已发/未发范围与生效记录保留；"停止≠撤销"可解释（R6） |
| V17 | 批准恢复后为曾发布车辆创建更高版本下发，目标=活动前值 60s（R6） |
| V18 | 全部目标车成功才可记完成；需恢复车全部确认才可记恢复完成；有未确认项禁止显示"全部恢复"（R7） |
| V19 | 逐车核查展示发布前值/期望值/生效值/结果/原因，不止活动总状态（R7） |
| V20 | 五组场景可在原型页面实际操作，失败原因可见可解释（`03-prototype-scope.md`） |
| V21 | 服务重启后业务结果仍可查询（共同要求 1） |
| V22 | 覆盖率 ≥85%（整体+各核心包）、-race 通过、go vet 通过（共同要求 6） |
| V23 | Git/PR/门禁/提交编号核验、AGENTS.md、双 Skill 及使用记录齐备（共同要求 3/4/8/9） |
| V24 | 自动部署成功，主分支发布版本与验收版本一致，冒烟通过（共同要求 7/8） |

## 8. 归档要求（取代原分散模板）

- **测试报告**（测试 Agent 产出）：被测分支/提交哈希、用例执行统计（通过/失败/阻塞）、覆盖率命令与原始数据、缺陷汇总（闭环/遗留）、假设清单、结论与遗留风险。
- **验收报告**（验收 Agent 产出）：验收基线与版本哈希（PR 合并版本 = 部署版本）、V1~V24 逐项结论与证据位置、整改项清单、复验记录、依赖的假设编号、最终结论（通过/有条件通过/不通过）。
- 两者数据必须一致可追溯：版本哈希、覆盖率、缺陷状态、场景结论。
