# 02-business-rules.md — 业务背景、现场情境与核心业务规则约束

> 本文件是业务语义的唯一工程化表述，与需求文档 §4~§7 对应；实现与检查均以本文件为速查口径，冲突时以题面原文为准。

## 0. 业务背景与现场情境（规则裁判依据）

**背景**：车云研发团队需要**临时**提高测试车辆的诊断日志频率来排查问题，但不宜一次性对全车队发布。研发提出配置申请 → 负责人审批 → 运营先向少量测试车辆发布 → 确认有效后再推广到剩余车辆 → 车端上报执行结果 → 负责人根据情况决定继续、停止或恢复原设置。

**现场**：本次排查涉及同一车队五台车辆。其中一台试点车在线，另一台离线；运营需要等到试点结果明确，才能继续推广。正式发布时，一台车应用失败，另一台因网络问题迟到回执。若直接把"已下发"当作"已生效"，或让旧回执覆盖新配置，就可能误判车队状态。

**停止语义**：停止活动不能声称已经撤销车端收到的配置；恢复原设置需要**另一轮可核查的下发**。

**目标**：实现一次非安全日志配置从申请到试点、推广及恢复的运营场景，让每台车的**期望值、实际生效值和失败原因**都能被解释。

**参与角色与业务起点**：
- 研发申请人：说明排查原因，选择车队与日志间隔。
- 审批负责人：批准或退回，复核试点和整体结果。
- 发布运营：执行试点、继续推广、停止未发送部分或发起恢复。
- 模拟车辆：认证后拉取配置并报告成功或失败。

**预置**：五台测试车辆及角色预置；配置**仅为日志上报间隔**，范围 **10~300 秒**，初始均为 **60 秒**；不涉及真实驾驶控制。

## 1. 申请与审批（R1）

- 申请必含：**排查原因、五台目标车辆（V1~V5）、新间隔**；间隔合法域 **[10, 300] 秒**（含端点，超出拒绝并提示）。
- **审批人 ≠ 申请人**：同一用户自审批必须返回明确拒绝并留痕。
- 退回（rejected）后申请人可修改再提交；重新提交后回到待审批。
- **批准后参数冻结**：修改已批准申请的任何参数（原因/车辆/间隔）必须拒绝；要改只能新申请。

## 2. 发布活动与试点门禁（R2）

- **同车队单一未结束活动**：车队存在 piloting/promotion_ready/promoting/recovering 状态活动时，创建新活动拒绝。已停止/已完成/已恢复完成的活动已结束，可创建恢复活动（假设 A6）。
- 试点固定 **2 台**（含 1 台在线、1 台离线）；**未选为试点的车辆不得提前取得活动配置**——拉取接口按"该车是否已被下发"过滤。
- **推广门禁**：两台试点均取得**有效成功回执**（不是已下发）才允许运营确认推广剩余三台；任一失败/超时 → 活动暂停，推广操作被拒绝并说明原因。禁止任何绕过检查直接推广的代码路径。
- 暂停后是否重试试点：按假设 A3（负责人复核后可重试，受 60s 约束），不推进则走停止。

## 3. 版本与生效模型（R3，核心）

- 车辆拉取只能得到**面向自己的最新已发布版本**；按车过滤，禁止返回其他车版本。
- **版本号按车辆独立单调递增**；恢复也产生更高版本（假设 A1），禁止活动级全局版本号。
- 每车持久化并区分：
  - **发布前值**：活动前该车生效配置（初始 60 秒）；
  - **期望值**：最近一次面向该车已发布版本的目标值（失败后仍指向失败版本，假设 A7）；
  - **已生效值**：最近一次有效成功回执对应版本的值。
- **下发动作只写期望值，不改生效值**；生效值唯一写路径 = 鉴权成功回执处理。
- 恢复 = 新一轮下发（版本更高、目标 60 秒），**禁止"停止即恢复"**的任何隐式实现。

## 4. 回执处理（R4）

| 回执 | 处理 | 禁止 |
|------|------|------|
| 当前版本成功 | 更新生效值 + 车辆结果，幂等（重复成功不重复记账） | 重复记账 |
| 当前版本失败 | 结果记失败 + 保留原因；**生效值不变** | 顺带清空/回滚生效值 |
| 旧版本成功（迟到） | 仅留痕，不覆盖生效值 | 旧覆盖新 |
| 未知版本（该车未发布过） | 拒绝 + 记录 | 静默接受 |
| 跨车回执（A 车身份回 B 车版本） | 拒绝 + 记录 | 仅凭回执里的车辆 ID 记账 |
| 鉴权失败 | 拒绝 + 记录 | 匿名记账 |

- 回执入库前必须完成：身份鉴权 → 车辆匹配 → 版本匹配，三者任一失败即拒绝留痕。

## 5. 超时与迟到（R5）

- 发布 **60 秒**未获有效回执 → 该车结果显示超时，**保留超时历史**（不得抹掉）。
- **当前期望版本**的迟到成功可把结果从超时翻转为成功，但超时历史仍保留。
- 失败回执不改变此前生效值（生效值保持上一个成功版本）。
- **已停止活动不因迟到回执自动重启**：迟到回执只更新车辆结果/生效值，绝不改活动状态。

## 6. 停止与恢复（R6）

- 停止仅阻止**未发布部分**继续下发；已发布记录、生效记录、已发/未发范围**全部保留**，页面不得显示"已撤销"。
- 负责人批准恢复后，运营**仅为曾发布过配置的车辆**创建恢复版本（目标 = 各车活动前值）；未下发过的车无需恢复。
- 恢复同样受 R3/R4 约束（更高版本、回执鉴权、幂等）。

## 7. 完成与核查（R7）

- **全部目标车辆确认成功**（有效成功回执）才允许负责人记活动完成。
- **所有需恢复车辆均确认恢复**才可记恢复完成；**仍有未确认项时页面禁止显示"全部恢复"**——这是硬性 UI 门禁，不是提示建议。
- 核查必须**逐车**展示：发布前值、期望值、生效值、结果（成功/失败/超时/未确认）及原因；**不能只展示活动总状态**。

## 8. 越权与留痕（R8）

- 以下操作一律明确拒绝并持久化留痕（谁、何时、什么操作、拒绝原因）：申请人自审批、运营绕过试点推广、车辆跨车回执、未认证拉取/回执、未授权角色执行发布。
- 账号预置，身份绑定会话/鉴权；禁止接受请求参数里的裸车辆/用户 ID 作为身份依据。

## 9. 预置数据、状态机与接口基准（实现速查）

### 9.1 预置数据

- 车队 `FLEET-01`，车辆 `VEH-01`~`VEH-05`，初始 `interval = 60s`；演示中一台在线、一台离线（如 VEH-02）用于网络分支。
- 账号：研发申请人 `dev`、审批负责人 `approver`、发布运营 `ops`、模拟车辆 `vehicle-01`~`vehicle-05`（各带预置 token）。

### 9.2 状态机

- 申请：`draft → pending → approved / rejected`；退回后可修改回 `pending`。
- 活动：`piloting → promotion_ready → promoting → completed`；`piloting → paused → stopped → recovering → recovered`。

### 9.3 接口与命名基准（建议，非题面强制；测试以实际接口清单为准）

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| POST | /api/activities | 申请人 | 创建申请（原因+5 车+间隔） |
| POST | /api/activities/:id/revise | 申请人 | 退回后修改再提交 |
| POST | /api/activities/:id/approve / reject | 负责人 | 批准/退回 |
| POST | /api/activities/:id/pilot | 运营 | 选择 2 台试点并发布 |
| POST | /api/activities/:id/promote | 运营 | 确认推广剩余 3 台（校验试点均成功） |
| POST | /api/activities/:id/stop | 负责人 | 停止活动 |
| POST | /api/activities/:id/restore/approve | 负责人 | 批准恢复 |
| POST | /api/activities/:id/restore/publish | 运营 | 为曾发布车辆创建恢复版本并下发 |
| POST | /api/activities/:id/complete | 负责人 | 记为完成 |
| GET | /api/activities/:id/progress | 负责人/运营 | 逐车进度（前值/期望/生效/结果/原因） |
| GET | /api/vehicle/config | 车辆(token) | 拉取面向自己的最新已发布版本 |
| POST | /api/vehicle/receipt | 车辆(token) | 上报成功/失败（版本、鉴权、幂等） |
| GET | /api/vehicle/:id/state | 车辆(token) | 查询自己期望值/生效值/失败原因 |

### 9.4 通用

- 教学时钟：超时阈值可配置，测试与演示必须走**同一规则代码路径**。
- 所有业务结果持久化，服务重启后可查询（V21）。
