# 05-git-workflow.md — 仓库、分支、提交与部署门禁

## 1. 仓库与分支

- 通过 **GitHub MCP** 创建独立仓库，保留工具名称、请求与结果、时间、仓库 URL；不得用手工/CLI 创建记录替代 MCP 证据。
- 默认主分支 `main`；业务代码、测试、原型、约束（含本文件与 AGENTS.md）、Skill、配置及文档变更**全部在 `dev/<题号>` 开发分支提交推送**，禁止直接 push main。
- main 配置分支保护：禁止直接推送、禁止强推、禁止删除；合并必须走 PR + 状态检查。

## 2. 提交规范

格式（一次 commit 只含一种类型，混合变更拆分提交）：

```
[类型] [版本号] [#工作项编号] 简洁中文描述
```

| 类型 | 版本号 | 工作项编号 |
|------|--------|------------|
| feat | 必填 | 必填，真实需求编号 |
| fix | 必填 | 必填，真实 Bug 编号（先登记 Bug） |
| hotfix | 必填 | 可事后补编号，保留补录记录（仅真实线上紧急修复） |
| opt | 必填 | 可选 |
| docs / test | 可选 | 可选 |

- 版本号 `v主.次.修订`；描述用简洁中文。
- **不得**因缺编号把功能变更伪装成 docs/test/opt。

## 3. meegle 编号核验（feat/fix 提交前）

```
meegle workitem get --work-item-id <数字编号> --project-key r17te9
```

- 由 AI 执行并保留实际输出；编号必须关联**相应需求或缺陷**，不得只验证"有这个数字"。
- 编号不存在或查询失败：未完成确认与有效核验前，该提交**不得视为合规**；禁止伪造编号或声称查询成功。

## 4. PR 与合并

- 前置条件全部满足后才可发起 PR：功能测试、单元测试与覆盖率门禁（≥85%）、并发/竞争检测、Agent 验收均通过。
- PR 描述附：需求与缺陷编号、变更说明、实际测试结果、覆盖率、验收报告及 AI/Skill 记录位置。
- PR 门禁通过才可合并；冲突或主分支更新引入变化时**重新检查最终待合并内容**。
- 优先采用**保留原始提交**的合并方式；若生成合并提交，消息按规范关联本次主要工作项；不得 squash 掩盖开发历史。
- 合并后必须可追溯：开发分支原始提交 ↔ PR 关系保留。

## 5. 部署门禁

- 仅允许对**经 PR 合并且门禁通过的主分支版本**执行正式教学环境发布；开发分支只可测试/预览部署。
- 流水线至少包含：质量检查（gofmt/vet）、单元测试与覆盖率门禁、构建、部署、健康检查、业务冒烟检查。仅提交 Dockerfile 或手工启动截图不算完成自动部署。
- **合并后对主分支实际合并版本重新执行质量门禁、构建和部署**；不得把开发分支旧版本的成功报告当作 main 已验证/已上线证据。
- 部署记录须含：部署地址、流水线运行标识、部署提交版本、结果、回退到上一可用版本的方法，以及首次部署失败时的撤销方式。
- 合并后发现缺陷：在开发分支修复 → 重新 PR，不直接改 main；回退记录保留原始历史。

## 6. 可审计交付与敏感信息

- 仓库保留索引：题号、需求与 Bug 工作项、分支、提交、PR、验收、部署的对应关系。
- 任何密钥、访问令牌、敏感数据不得进入仓库、日志、截图或视频；发现即从提交中清除并记录处理过程。
